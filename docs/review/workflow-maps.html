What stands out so far

  1. Repeats are handled in the database, not left to the agent. A unique index makes one thread one item, done and snoozed items included. Fingerprints decide whether a repeat groups, reopens or wakes, the priority only climbs, and a repeat never rewrites what someone wrote. None of that depends on the agent remembering what it filed before.
  2. The intake rules live outside the database. The action gate, the priority tiers, the sender map and the mail types are agent rules and workspace configuration. The database keeps the result (priority, area, title) but not the reason, and a skipped thread leaves no trace at all.
  3. A run leaves no record inside rheoStream. Each create has its own audit row, but the run's window, its counts and a failed run exist only in the result line it prints, outside the product. Nothing in the screens can say when mail was last read or whether the last run failed.

Questions for the team

  1. Should a "paid" or "resolved" notice close its item? Current already has current_close_by_source, which closes the item for a thread and clears its fingerprints so the next real message reopens it. The rules skip these notices instead, so a paid bill's item stays open until someone closes it by hand.
  2. Should a run leave a record in rheoStream? The window, the counts and a failure live only in the result line. A run record, or a job row for scheduled runs, would let the screens show when mail was last read and whether the last run failed.
  3. Should the mail type be a field? Type: is the body's first line, so the queue can't filter to every bill or every inquiry. A type column would also make the labels a list the workspace can see.
  4. Should the sender map live in the workspace? It sits in agent configuration today, and item.area keeps only the result. A small table of senders and areas would make the mapping visible and editable from the screens.
